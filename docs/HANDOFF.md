## Что это за сайт в двух абзацах

Контент лежит в `data/*.json` — это единственный источник правды. PHP-сборщик
(`php app/bin/build.php`) превращает его в статический HTML: 644 страницы примерно
за секунду. Самописная админка правит те же JSON формами и после каждого сохранения
пересобирает сайт целиком. Хостинг нужен обычный, с PHP 8.1+, без базы данных.

Сайт заменяет действующий, домен не меняется. Главная ценность работы — не дизайн,
а карта переноса адресов: 747 старых URL разобраны так, чтобы накопленный поисковый
вес не потерялся.

## Первые шаги для того, кто принимает проект

```bash
git clone https://github.com/mihailburmasov/zdso-chelyabinsk.git
cd zdso-chelyabinsk
php app/bin/build.php          # соберёт dist/, должно быть 644 страницы
node tools/check.mjs           # все проверки собранного сайта
node tools/serve.mjs 8098      # посмотреть dist/ в браузере
```

Чтобы открыть админку локально, нужны две вещи, которых в репозитории нет намеренно:

```bash
cat > app/config.local.php <<'PHP'
<?php
return ['site_url' => 'http://127.0.0.1:8099', 'base_path' => '', 'admin_local_no_gate' => true];
PHP
php app/bin/admin-setup.php <пароль>
php -S 127.0.0.1:8099 app/dev-router.php      # сайт + админка + приём заявок
```

`app/config.local.php` на сервер не заливается никогда — у сервера свой
`config.server.php`. Пароль админки и сессии лежат в `storage/`, который тоже вне git.

## Что делать дальше, по порядку

Полный список — в [CLIENT-REQUESTS.md](CLIENT-REQUESTS.md). Коротко:

- **PHP 8.1+ на хостинге.** Сейчас сервер отдаёт `X-Powered-By: PHP/5.6.40`.
  Без переключения версии админка просто не запустится.
- **Какой телефон и почта верные.** На старом сайте подпись и ссылка расходятся:
  на экране `+7 (351) 219-90-00` и `info@zdso.ru`, в ссылках `tel:+73517766405`
  и `mailto:masterskie174@mail.ru`. Мы взяли то, что указано в реквизитах компании.
- **Ссылки на MAX, Telegram, WhatsApp.** Пока пустые — кнопки на сайте серые.
- **Доступы к Яндекс.Вебмастеру и Метрике (счётчик 41346549).** Нужны не только для
  настройки: без них нельзя проверить главное решение редизайна — см. пункт 2.

### 2. Подтвердить решение по канонической схеме каталога

Мы выбрали новую схему `/catalog/zapasnye-chasti-i-komplektuyushchie/…` — она связана
внутренними ссылками и отдаёт корректные title, а старая схема не связана ни с одной
страницы сайта. Но **решение принято по данным живого сайта, а не по трафику**: доступа
к Метрике и Вебмастеру не было.

Перед релизом открыть «Страницы входа» за два года и список внешних ссылок. Если трафик
идёт на старую схему — карту надо развернуть. Технически это правка одной колонки
в `seo/redirects.csv` и перегенерация `.htaccess`, работы на полчаса.

Остальные решения, меняющие адреса, перечислены в конце [AUDIT.md](AUDIT.md) —
их тоже стоит проговорить с заказчиком.

### 3. Поднять стенд и прогнать то, что нигде ещё не исполнялось

Это самый важный невыполненный пункт. Правила `.htaccess` ни разу не работали под Apache:
ни PHP-роутер, ни сборщик их не исполняют.

```bash
# на стенде собирать так: закрытый robots, noindex, относительные цели редиректов
STAGING=1 php app/bin/build.php
STAGING=1 node tools/make-seo.mjs

# после заливки — обязательная проверка
node tools/check-redirects.mjs https://стенд.адрес
```

Скрипт проверяет каждое правило (один 301, затем 200, без цепочек) и отдельно варианты
хоста — `http://`, `www.`, `http://www.` — на 15 адресах. Именно там у старого сайта
была цепочка из трёх переходов с уходом на незащищённый `http`.

На стенде же проверить три вещи, которые зависят только от хостинга:

- какой переменной сервер сообщает о HTTPS (`HTTPS` или `X-Forwarded-Proto`);
  ошибка здесь даёт бесконечный редирект — возможно, это и был «циклический редирект»
  на старом сайте;
- не включён ли в панели хостинга принудительный HTTPS: если он редиректит до Apache,
  `.htaccess` не сможет заменить 302 на 301;
- работают ли `mail()` с адресом на домене и доступ к `api.telegram.org`.

### 4. Прогнать полный цикл заливки

`deploy.php` достался из проверенного проекта, но пути кода и контента я переписал под
эту раскладку, и сам обмен по FTP здесь не прогонялся.

```bash
php app/bin/deploy.php list    # что поедет как код, что считается контентом
```

Ожидаемый вывод: 1027 файлов кода (ядро, статика, фото оформления в `img/bg`, 913 старых фотографий и их webp-двойники),
**ноль** файлов в `upload/media` — это папка клиента; и 48 файлов контента, из них 34 — каталог.

После `init` на реальном хостинге проверить цикл целиком: создать позицию в админке,
загрузить фото, затем `push` и `pull` — и позиция, и фото должны уцелеть.

**Перед первым `pull` сделайте `git init` и коммит.** `pull` перезаписывает `data/`
и `public/upload/media`; скрипт на отсутствие репозитория ругается и не даёт продолжить
без `--force` — это защита, а не помеха.

### 5. Релиз и две недели наблюдения

Порядок в [CHECKLIST.md](CHECKLIST.md). Два пункта, на которых чаще всего горят:

- **Снять закрытие индексации.** Собрать без `STAGING`, проверить `robots.txt` руками
  после заливки. `node tools/check.mjs` падает, если robots открыт, а `.htaccess` остался
  стендовым — но на боевом сервере проверить всё равно глазами.
- **Сохранить бэкап старого сайта и базы** с проверкой восстановления. Возможность
  откатиться за час обязательна.

## Чем проверять

Все проверки воспроизводимы и ничего не чинят сами.

| Команда | Что проверяет |
|---|---|
| `node tools/check.mjs` | ссылки, картинки, canonical, H1, метатеги, карты сайта, микроразметка, соцсети, рассинхрон robots и `.htaccess` |
| `node tools/shots.mjs` | вёрстка и горизонтальный выезд на 360/768/1280/1920 |
| `node tools/check-search.mjs` | поиск по номеру чертежа, 16 написаний, в настоящем браузере |
| `node tools/check-forms.mjs` | формы заявок: тип, поля, надписи на кнопках |
| `node tools/check-admin.mjs <пароль>` | круговой тест админки со сверкой всех файлов данных |
| `node tools/check-admin-add.mjs <пароль>` | добавление новости, статьи и позиции каталога через формы |
| `php tools/check-mime.php` | какие типы файлов принимает форма «прислать чертёж» |
| `php tools/check-mail.php` | сборка письма с вложениями |
| `node tools/check-redirects.mjs <адрес>` | редиректы на живом сервере |

Браузерные проверки требуют запущенного `node tools/serve.mjs 8098`,
админочные — `php -S 127.0.0.1:8099 app/dev-router.php`.

## Грабли, на которые уже наступили

Это не теория — каждый пункт стоил здесь времени.

- **Админка округляла дробные числа.** Поле типа «число» приводило значение к `int`,
  и массы деталей 0,6 и 2,32 кг превращались в 0 и 2. Чинится в `clean_value()`;
  регрессию ловит `check-admin.mjs`, который сверяет контрольные дробные веса.
- **Админка съедала поля, которых нет в форме.** Таблицы внутри блоков услуг и статей
  пропадали при первом же сохранении. Теперь неизвестные ключи проносятся как есть
  (`passthrough_value()`), а `check-admin.mjs` сверяет все файлы данных со снимком.
- **`usort` по ассоциативному массиву убивает ключи.** `catalog/sections.json` — объект,
  ключ записи это имя файла её позиций. Сортировать только `uasort`.
- **В PHP имя переменной может содержать байты 0x80–0xFF.** Строка `"«$label»"`
  разбирается как переменная `$label»`. Внутри строк только `{$label}`.
- **Адреса страниц выводятся из слага, а не хранятся.** Поля «полный адрес» убраны
  из форм: вручную заданный адрес мог перезаписать чужую страницу. `emit_page()`
  бросает исключение, если два адреса метят в один файл, и сохранение откатывается.
- **Git Bash превращает `/zdso-chelyabinsk` в windows-путь.** Для сборки демо нужен
  `MSYS_NO_PATHCONV=1`, иначе `base_path` станет `C:/Program Files/Git/…`.
- **Длина пути в Windows.** Самый длинный адрес каталога — 201 знак. Собирать демо
  в глубокую временную папку нельзя: `git add` упадёт на «Filename too long».
  Собирайте в короткий корень вроде `D:/tmp/zp`.
- **`tools/make-data.mjs` — разовый импорт.** Он удаляет и пересоздаёт файлы разделов.
  После запуска сайта его запускать нельзя: позиции, добавленные менеджером, исчезнут.
  Безопасны `make-photos`, `make-webp`, `make-site-photos`, `make-seo`, `make-semantics` и все `check-*`.
- **Фотографии со старого сайта нельзя удалять через медиатеку.** Файлы в
  `upload/iblock`, `upload/medialibrary` и `upload/resize_cache` считаются кодом,
  и следующий `push` зальёт их обратно.

## Что сделано не до конца — и это нормально

Здесь нет «почти готово»: перечислено ровно то, что осознанно оставлено.

- **Описания назначения деталей** написаны по 20 шаблонам, подобранным по типу детали.
  Это лучше пустоты и лучше, чем у конкурентов, но уникальным текстом для каждой
  из 560 позиций не является. Уникализировать стоит ходовые позиции: плиты, брони,
  подпятники.
- **ТТХ машин не выдуманы.** Блок на страницах `/tehnika/…` не выводится, пока заказчик
  не пришлёт характеристики. Всё остальное на этих страницах работает.
- **Взрыв-схем узлов нет** — нужны чертежи от заказчика. Вместо них работает группировка
  деталей по узлам (правила в `data/units.json`).
- **Шесть разделов ждут материалов** и показывают заметку «раздел готов к наполнению»:
  `/company/certificates/`, `/company/partners/`, `/company/reviews/`, `/company/staff/`,
  `/company/production/`, `/projects/`.
- **Автосборка демо не подключена.** Файл `.github/workflows/deploy-pages.yml` лежит
  в рабочей копии, но не в репозитории: у токена `gh` нет права `workflow`. Включается
  двумя командами, они в README.
- **Прайс по конусным дробилкам** — заглушка: на старом сайте там стояло
  «Type text here...». Нужна таблица в Excel от заказчика.

## Чего делать не нужно

- Не править HTML в `dist/` — он производный и перезаписывается при каждой сборке.
- Не менять адреса существующих страниц каталога: они уже в индексе, а карта переноса
  рассчитана именно на них.
- Не делать региональные поддомены и страницы городов «из воздуха»: страница города
  без уникального смысла получает фильтр за переспам. Заложена честная география
  поставок на `/delivery/`.
- Не заводить новый счётчик Метрики: в 41346549 накоплена история.
- Не возвращать Twitter и Facebook — удалены по требованию заказчика, включая `sameAs`.
